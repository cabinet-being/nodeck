# Робота агентів у nodeck

## Керування й делегування

Головний агент визначає межі задачі, план і критерії прийняття, розподіляє роботу, інтегрує результати та перевіряє сукупні зміни. За потреби використовуй спеціалістів, визначених у локальній `.codex/agents/`; не запускай усі ролі автоматично. Якщо користувач просить лише обговорення або план, не змінюй файли.

- Передавай спеціалісту стислий пакет контексту: мету, наявні докази, точні дозволені шляхи, заборонені дії, критерії прийняття, потрібні перевірки й дозвіл або заборону коміту. Повну історію чату передавай лише за потреби.
- Для паралельної роботи призначай непересічні шляхи запису; залежні зміни виконуй послідовно. Спеціалісти не делегують далі.
- Не розширюй межі задачі непомітно. Про блокери та потрібні зміни поза призначеними шляхами спеціаліст повідомляє головному агенту.
- Дефекти, виявлені `tester`, передавай головному агенту: він призначає виправлення `developer` і перевіряє результат.
- Якщо клієнт не підтримує вибір іменованої ролі, головний агент читає відповідний TOML і явно передає інструкції та профіль агенту. Локальні визначення ролей не додавай до комітів.

| Роль | Дозволені зміни | Результат |
| --- | --- | --- |
| `scraper` | Жодних файлів або комітів | Цільові факти з шляхами й рядками, явні невідомі |
| `architect` | Жодних файлів або комітів | Архітектурний аналіз і конкретний план у чаті |
| `developer` | Призначений продуктовий код, UI та ресурси, переважно `backend/src/` і `frontend/src/` | Реалізація та перевірка |
| `tester` | Призначені тести, fixtures і тестові допоміжні файли, переважно `backend/tests/` | Тести, результати й відтворювані дефекти |
| `tech_writer` | Призначена документація, зокрема `README.md` | Документація за фактичними змінами |

`tech_writer` не редагує код, коментарі коду чи docstrings. `tester` не виправляє продуктовий код і не послаблює тести, щоб приховати дефект. `architect` і `scraper` не створюють навіть тимчасових файлів і не виконують команд, що змінюють стан проєкту. Спеціалісти не редагують `AGENTS.md` або визначення власних ролей. Це поведінкові межі; головний агент перевіряє їх дотримання.

Профілі з `.codex/agents/`: `scraper` — `gpt-6-luna` / `low`; `architect` — `gpt-6-sol` / `high`; `developer`, `tester` і `tech_writer` — `gpt-6-sol` / `medium`. Явні побажання користувача мають пріоритет. Якщо модель недоступна, повідом головному агенту перед заміною.

## Мінімальний контекст

1. Перевір `git status --short` і збережи чужі незавершені зміни.
2. Починай з `README.md` та цільового модуля. Шукай символи через `rg`, потім читай відповідні виклики й тести.
3. Для API дивись `backend/Program.cs`, відповідні файли в `backend/src/` та тести в `backend/tests/`. Для UI дивись сторінки й компоненти в `frontend/src/`. Для схеми даних дивись `database/init/`.
4. Документація допомагає орієнтуватися; поточний код є доказом поведінки. Не читай увесь проєкт за замовчуванням.

Не скануй масово `node_modules/`, `dist/`, `bin/`, `obj/`, `volumes/`, кеші, логи, великі згенеровані файли й бінарні дані. Для широкого пошуку спершу доручи `scraper` конкретне питання; типовий звіт — до 600 слів із короткими витягами й посиланнями на рядки.

## Реалізація та перевірка

- Перш ніж додавати helper або дублювати логіку, знайди наявного власника поведінки та всі її використання.
- Зберігай узгодженість API, моделей, збереження даних і UI. Якщо змінюєш контракт, перевір відповідні виклики та тести.
- Для зміни backend запускай відповідні тести через `dotnet test backend/tests/MyApp.Api.Tests.csproj`. Для зміни frontend запускай `npm run build` у `frontend/`. Додаткові перевірки обирай за ризиком зміни. Не заявляй про проходження перевірки без її запуску.
- Не редагуй `.env` або дані в `volumes/` як частину звичайної зміни коду. Не додавай до Git секрети, локальні налаштування, кеші або результати збірки.
- Оновлюй лише документацію, яку зачепила фактична зміна. У звіті вказуй виконані перевірки, їх результати та обмеження.

## Git-дисципліна

- Завершений логічний етап коміть після відповідної перевірки й огляду головним агентом, якщо користувач явно не заборонив коміти. Плануй такі контрольні точки заздалегідь.
- Спеціаліст комітить лише за явним дорученням головного агента; інакше коміт робить головний агент. Використовуй доречний conventional commit, наприклад `feat:`, `fix:`, `test:` або `docs:`.
- Додавай до staging лише явні шляхи зі своїми дозволеними змінами. Не використовуй `git add .` або `git add -A`; перед комітом переглянь staged diff.
- Якщо вже staged сторонні зміни, повідом про блокер. Не включай їх до свого коміту й не прибирай зі staging самостійно.
- Не перезаписуй і не відкочуй роботу користувача чи інших агентів. Спеціалістам заборонені `push`, `merge`, `amend`, `reset` і `clean`.
- Локальні `.codex/agents/`, сесії, пам’ять, плани й тимчасові результати не коміть. Спільні `AGENTS.md`, документація, вихідні файли та тести залишаються під контролем версій.

## Звіти спеціалістів

Кожен спеціаліст повідомляє виконану роботу або висновки, фактичні перевірки та результати, змінені файли (або їх відсутність), невирішені питання й блокери. Відділяй факти від гіпотез; для тверджень про код наводь шляхи й рядки.

Для дефекту `tester` надає проблему, передумови, кроки відтворення, очікувану й фактичну поведінку, докази (тест, помилка або лог) та можливі причини з місцями в коді. Помилки середовища або налаштування позначай окремо від дефектів продукту.
